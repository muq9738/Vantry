# Vantry 0.1.23

Fix T3 streaming updates falling back to full snapshots at normal Core output cadence.

- Separate committed Core event coverage from per-subscription wire sequencing. One Core event can now produce several ordered row updates without exhausting a cursor interval or suppressing later Core events.
- Keep user-message and user-turn-item timestamps tied to submission rather than assistant output, eliminating false changes to user rows.
- Keep snapshot fallback sequences increasing within a subscription. Reconnect always establishes a fresh epoch using a complete authoritative snapshot; transport resume cursors are never passed to Core.
- Preserve full-snapshot fallback for structural, run-state, visibility, and archive changes.

The previous 41-run synthetic fixture only tested an ample cursor interval. A real temporary Core emitting every 20ms reproduced 78 full snapshots and no deltas. The same workload after this fix produced two structural snapshots and 150 row updates, reducing decoded JSON payload from 1,209,295 B to 295,051 B (approximately 75.6%). This is a controlled workload, excludes WebSocket compression and TLS overhead, and is not a universal bandwidth prediction.

Regression coverage checks single-event windows, Core cursor advances of one to three, wire cursors ahead of Core, both thread and shell snapshot fallback, full-state reconstruction, reconnect, and post-reconnect updates. T3, remote-access, and application tests pass with the Go race detector.

This patch does not introduce a new relay protocol or require a linkd update. Existing gzip, HTTP/2, and HTTP/1.1 fallback remain unchanged. macOS packages use the existing local signing identity and are not Apple-notarized; Windows x64 remains a cross-compiled preview without native remote-desktop hardware validation.
