# Vantry 接入 Alma iOS 与 T3 移动协议退役方案

目标是让用户在电脑上只开 Vantry，用原版 Alma iOS 扫码，打开电脑上的同一条会话。手机优先走局域网，跨网走自建 linkd。电脑和手机可以接力发消息、查看工具进度、处理审批、跟踪子任务和 Todo。Vantry Core 持有会话历史与执行状态。移动应用的安装和更新沿用 Alma 官方渠道，自研 Vantry-iOS 退出发版计划。

本文是实施设计。协议基线取 Alma 桌面端 `0.4.567`、官方 `alma-relay 1.5.0` 和独立 `linkd v0.1.2`。验收记录另行填写实际 Alma iOS build、Vantry 与 linkd 提交号。

## 1. 接入方式与代码归属

| 位置 | 变更 | 对外约定 |
| --- | --- | --- |
| 独立 linkd 仓库 | 在专用域名承载 Alma 中继协议，动态登记在线电脑 | 电脑连 `/agent?th=<tokenHash>`，手机连 `/c/<routingToken>/…`。同一服务继续按现有规则承载 Vantry 原生设备和桌面连接 |
| Vantry Service | 启动 Alma 主机端，管理配对、局域网监听、到配置中继的主动回连 | 生产环境回连自建 linkd。相同的主机端也能连官方 `alma-relay` 实现，作为协议互通测试 |
| Vantry Core | 沿用已有会话、运行、工具调用、待处理请求、子任务和提交游标 | 桌面与手机的命令走同一处理入口，同一项批准或派发只生效一次 |
| Vantry 桌面 | 在设备设置显示 Alma 配对码、设备、撤销和连接状态 | 展示最近一次已认证连接的直连或中继状态，区分中继在线和手机在线 |
| Alma iOS | 使用原版客户端提供的会话、操作、Markdown 与媒体视图 | Vantry 在电脑端把 Core 记录映射成客户端识别的消息和操作，设备上沿用 Alma 的排版 |

T3 的启动、移动监听器和回连通道接在 Vantry Service。实现时从这里替换，独立 linkd 的通用 `route/channel`、原生会话和 TURN 服务按原用途继续运行。[Service 启动与回连](../apps/service/src/main.rs) · [主机通道分派](../crates/connectivity/src/peer.rs) · [linkd 原生协议](https://github.com/muq9738/linkd/blob/b9bfbbedcf1842945d9db6da5d7f03c64178a9f9/docs/protocol.md)

## 2. linkd 与 alma-relay 的互通合同

**联调入口已经实测，发布入口采用动态注册。** 在回环网络上，原版 linkd 和 alma-relay 互相接收对方的主机注册请求均返回 `404`。官方测试 agent 连官方中继协商到协议 3，二进制往返一致。给原版 linkd 添加下面这类 `sessions.httpUpstreams` 规则，再用 `linkd agent` 将 `alma` 通道接到测试后端，手机路径升级为 WebSocket，4096 字节往返一致，未映射的令牌返回 `404`。这项记录覆盖字节转发；手机加密握手和界面另有验收用例。

固定路由示例（字段取自 linkd v0.1.2，域名、路由和令牌是示意值）：

```json
{
  "host": "mobile.example.com",
  "prefix": "/c/EXAMPLE_ROUTING_TOKEN/",
  "stripPrefix": true,
  "route": "example-device-route-01",
  "channel": "alma"
}
```

这条规则适合先把一台开发机接通。发布版本在 linkd 内实现 Alma agent 注册和转发，每台电脑主动登记自己的 `tokenHash`。换配对码、加电脑和重连都通过协议完成，运维只配置一次域名和注册凭据。最终用户运行一个 linkd 服务；官方中继进程仅作开发测试的参照。

| 合同 | 实现方式与判定 |
| --- | --- |
| 登记与寻址 | 核对 `th`、注册帧中的哈希与注册凭据。内存登记 `tokenHash → agent socket`，按官方规则处理重复注册、旧连接退出和注册失败。手机路径中的路由令牌经 SHA-256 查表，永不作为业务授权 |
| 协议协商与传输 | 实现协议 1 的 JSON 帧、协议 2 的二进制帧与请求体流、协议 3 的逐流 `window/ack`。覆盖 HTTP/SSE、WebSocket 的打开与关闭、取消、超限及慢消费者。版本号随实际实现逐版启用 |
| 中断恢复 | 按 1.5.0 的 `resume/resumed` 恢复双方仍持有的子连接，重置逐流额度；宽限到期释放缓存。密文序列中断时关闭对应加密会话，由手机重新握手并从 Core 恢复历史 |
| 可选能力 | 对本部署没有配置的推送通道，按官方 `pushed` 帧返回 `unsupported`。审批和任务完成状态可在手机前台连接或重连后取得；系统后台推送另按 Alma 的签名与通知渠道验收 |
| 版本互测 | 官方 `FakeAgent → linkd` 检查帧和生命周期；`Vantry agent → 官方 alma-relay` 检查主机兼容性；`Vantry agent → linkd → 原版 Alma iOS` 验收产品行为。注册、错误码、流控、断线场景在前两组运行同一套用例 |

协议帧和大小限制直接以固定版本的规范与测试为准。诊断日志记录路由结果、错误阶段、协商版本和连接数，屏蔽完整配对链接、`/c/` 后的令牌、注册凭据和会话密文内容。[官方传输协议](https://github.com/yetone/alma-relay/blob/95bc1423049b0f470964896371bbbd47622f1241/docs/PROTOCOL.md) · [官方测试 agent](https://github.com/yetone/alma-relay/blob/95bc1423049b0f470964896371bbbd47622f1241/test/fake-agent.mjs) · [linkd 路径转发实现](https://github.com/muq9738/linkd/blob/b9bfbbedcf1842945d9db6da5d7f03c64178a9f9/transport/ingress.go)

## 3. 配对、直连和回退

1. 用户在 Vantry 开启 Alma 手机访问。Service 生成并私密保存 256 位随机连接码，按目标版本的 Alma 规则派生路由令牌与登记哈希。公网连接使用 WSS，连接码仅进入本机显示的 `alma://connect?u=<编码后的中继地址>&k=<连接码>&e2e=1`。用固定输入验证派生结果；在协议互测中验证密钥协商、双向密文、计数器和重放拒绝。
2. 首次配对以自建中继可达为基线。手机据二维码发起连接，Vantry 只允许加密入口 `/__alma_e2e__`，在端到端握手成功后才开放设备可访问的业务接口。官方中继传来的明文业务请求按协议拒绝。身份、密钥和收到的业务命令在电脑上校验。
3. 手机通过已认证的 `/__alma_lan__` 获取 `{ "hosts": [...], "port": ... }`。Service 发布当前可达网卡候选，在换网或监听地址变化后更新。手机可在局域网直达同一加密入口。首次配对、已配对后中继离线冷启动是两项独立测试。
4. Wi‑Fi 切蜂窝时，手机通过 linkd 恢复同一台电脑的会话；回到可达 Wi‑Fi 时允许客户端重新选择直连。两条路径复用同一 Core 身份、相同对象 ID 和去重记录。连接切换只终止旧订阅，Core 中执行的任务继续运行。
5. 用户重置配对时撤销旧登记、关闭旧直连和中继加密会话并轮换连接码。联调时确认该 iOS build 是否提供可验证的独立设备身份；具备此身份时按设备撤销，否则桌面明确提供“重置所有手机配对”，避免把共享密钥描述成单设备凭据。

本机 Alma 桌面安装包的 `alma-server/lib/server.mjs` 可用 `alma://connect?u=`、`/__alma_e2e__`、`/__alma_lan__` 定位上述协议入口。手机选路时序以目标 iOS build 的测试结果为准。[Alma 官方配对说明](https://alma.now/docs/guide/installation) · [Alma 的直连和远程使用说明](https://alma.now/docs/zh/features/herdr)

## 4. 同一条会话如何在两端工作

Alma 主机端通过 Core 私有接口读取已提交记录。第一步用专用测试会话，让原版手机执行打开、发送、停止、审批、查看子任务等动作，在主机端记录脱敏后的请求方法、路径、必要字段、响应与事件顺序。已安装 Alma 包中可定位 `/api/threads`、`/api/threads/:threadId/messages`、`/api/threads/:threadId/subagents/live`、`/api/herdr/answer`、`message_streaming` 与 `thread_messages_sync`。这些是定位入口的线索。以手机实际使用的会话或 Agent 视图确定接口组合，分别固定历史载入、实时更新和写操作样本。

| 能力 | 手机表达和写回 | 两端一致性要求 |
| --- | --- | --- |
| 会话与消息 | 列出授权范围内的项目、线程，读取历史、发消息、停止运行、继续对话。稳定映射 thread、run、message 标识 | 在任一端发送，另一端看到同一条记录；手机中途加入能读到已产生的前缀，结束后能重开完整回复 |
| 工具调用 | 用 Alma 支持的工具消息结构映射 `toolCallId`、参数、进行中、结果、失败和取消；长输出沿用 Core 提供的预览或详情 | 一个调用 ID 从开始更新到结束；并行调用按各自 ID 合并；刷新后保留原顺序和最终状态 |
| 审批与提问 | 将 Core 待处理请求映射成 Alma 的确认或选项交互，提交时带回请求身份，在主机校验作用域与待处理状态 | 手机批准后桌面同步收起；若桌面先响应，手机看到已处理状态。超时、撤销和过期选项都以 Core 为准 |
| 父子任务与编排 | 投影父线程、子任务、执行设备、状态、摘要和结果。优先映射到 Alma 子 Agent 视图；只有客户端动作能回传稳定标识时才展示可执行操作 | 两端看到同一个子任务；手机的确认、取消、继续对应同一 Core 命令。远端子任务沿现有编排归属执行 |
| Todo | 复用 `vantry_todo_write` 等已有工具语义，提取标题、顺序、状态和 `activeForm`。优先适配 Alma 原生 Todo；需要时更新同一条可读清单 | 手机重连后只展示当前 run 的最新有效清单。置顶、折叠和完成数分别验收；清单文字不代替完成状态验证 |
| Markdown 与排版 | 保留段落、标题、列表、表格、引用、代码语言、附件引用和工具消息边界；用手机支持的富文本或附件格式表达 | 流式追加不打散代码块。以中英文混排、长表格、长代码和消息内多个内容块做双端样本 |
| 图表与交互块 | Mermaid、数据图优先投影成手机可渲染的图或 artifact；否则由主机从同一数据生成图片，并附可读标签或数据表。`ask/dispatch` 走有请求 ID 的交互 | 比对节点关系、坐标、单位和数值。图表静态呈现、缩放与按钮操作分别记录，批准和派发须经可验证的写回入口 |

Core 保留原始结构，手机表示由适配层按读请求生成。图片与附件走设备授权的资源入口，绑定所属会话；用户发来的文本及模型输出中的代码块只作为内容，实际执行动作必须对应有效的 Core 请求。[Core 协议对象](../crates/protocol/src/api.rs) · [编排与任务详情](../apps/service/src/orchestration.rs) · [Todo 解析](../apps/desktop/src/state/todo.rs) · [Vantry 内容块](../apps/desktop/src/views/visuals.rs)

### 断线、并发及重试

- **读。** 从包含提交游标的 Core 快照生成手机历史，再订阅该游标之后的事件。写入同一消息或工具的更新以稳定对象 ID 合并。游标缺口、服务重启或客户端只支持全量同步时，重新取得权威快照；保持历史和实时消息使用相同 ID。
- **写。** 手机提供稳定操作 ID 时，将它与设备、操作类型绑定到持久 Core 命令 ID。批准、选项回答、子任务确认还要绑定原请求 ID，由主机原子消费。若某版手机发送消息缺少稳定重试 ID，响应丢失后先同步历史；不按文本哈希合并用户两次有意发送的相同内容，不自动重发结果未知的命令。
- **切换。** 直连与中继短暂重叠时，旧订阅停止发布，新订阅接续 Core 提交位置。分别测试切网发生在工具执行中、审批已提交但回执未到、图表附件传输中三种时刻。

## 5. 实施顺序与 T3 退役

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1 · 锁定手机协议 | 固定 iOS build；用隔离测试数据记录二维码、握手、首次请求、会话和 Agent 两类界面的输入输出。创建可重放的脱敏样本 | 用 Vantry 主机端连官方中继，原版手机能扫码、读一个 Core 线程、发消息并收到流式回复 |
| 2 · 接入 linkd | 在独立 linkd 实现动态注册与数据转发；Vantry 加入 LAN 候选、设备设置、撤销和路由状态。固定路由用于早期隔离联调 | 两组跨实现协议测试通过。手机在 Wi‑Fi、蜂窝和回到 Wi‑Fi 三段操作同一会话；每段有实际路径证据 |
| 3 · 双端功能 | 实现上表的工具、审批、编排、Todo、富文本和图表。把稳定的字段样本和断线用例纳入对应仓库回归 | 下节用户旅程通过，记录 iOS 的实际呈现方式；所有可执行操作均有 Core 状态变更证据 |
| 4 · 切换入口 | 桌面设备页默认展示 Alma 配对。旧 T3 地址、二维码和新配对入口下线；升级说明引导既有手机重新配对 | 老版本数据升级后桌面仍能访问原会话、历史、原生配对设备和执行中的任务。用单独迁移用例检查共用监听器和桌面网关 |
| 5 · 清理 | 移除 `T3Server`、T3 专用凭据兑换、设置项、通道分派、旧文档和专用测试；将共用的设备、桌面和 Core 接口先迁回各自模块 | 默认构建及启动不再启用 T3；原生会话、远程桌面、Alma LAN 与中继均通过回归。自研 iOS 工程单独归档 |

切换前记录当前发布版本和路由配置。灰度失败可关闭 Alma 新入口、恢复上一版本服务与路由，再由桌面读取同一 Core 数据。迁移测试使用旧版数据副本；T3 凭据和 Alma 配对材料分开管理，已有 T3 配对不会自动获得 Alma 访问权。[当前 T3 适配器](../crates/connectivity/src/t3compat.rs) · [原生连接与桌面网关说明](native-connectivity.md)

## 6. 真机验收

| 用例 | 操作 | 通过条件 |
| --- | --- | --- |
| 同一条任务贯穿双端 | 桌面发起带三项 Todo 的任务，执行两个并行工具，派发子任务并生成带单位的图；在工具运行中用 iPhone 打开 | 桌面与手机的线程、运行、工具和子任务逐项对应。手机清单随步骤完成更新，图表标签和数值一致 |
| 两端竞争同一审批 | 手机与桌面接近同时回答；分别覆盖两端先到以及回执丢失 | Core 只接受一次有效决策，工具或子任务只启动一次。两端最终显示同一决策和结果 |
| 路由可证 | 首次扫码后，关闭测试中继，在同一 Wi‑Fi 冷启动手机并收发。恢复中继，切蜂窝再发送。回到 Wi‑Fi 再打开会话 | 电脑分别观察到 LAN、linkd、LAN 的已认证连接。检查历史连续、无重复消息，关闭测试中继期间 LAN 可以独立工作 |
| 断线补齐 | 中断 agent 回连，期间工具完成、子任务返回；恢复后重开手机 | 手机补齐完成事件、Todo 和结果。日志能区分子连接恢复、重新握手与全量同步 |
| 配对轮换与作用域 | 重置配对，分别尝试旧手机、旧路由令牌和新二维码；从已授权线程尝试读取另一作用域的资源 | 旧加密连接及时关闭，旧材料无法读取或执行，新配对可继续访问授权历史。资源和命令通过同一授权检查 |
| T3 升级与回退 | 从带 T3 配置、原生设备和历史任务的数据副本升级，再按回退流程恢复 | 升级后只展示 Alma 手机入口；原有桌面会话和执行记录可读；回退后原生设备和数据可用 |

每次发布保留一份验收记录，包含四端版本（iOS、Vantry、linkd、官方参照中继）、实际路径、脱敏对象 ID、Core 命令结果和手机截图。协议互测证明传输兼容，真机操作与 Core 记录共同证明双端会话功能完成。
